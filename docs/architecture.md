# Архітектура та межі модулів

Застосунок складається з React-клієнта, HTTP API, фонового worker і PostgreSQL. Локально worker може працювати в процесі API; Docker Compose запускає його окремо. Обидва варіанти використовують ту саму чергу та фінансові транзакції. Додаткових ORM, контейнерів залежностей і бібліотек глобального стану немає.

## Структура

```text
src/
  client/
    App.tsx                 компонування екрана, фільтр і сповіщення
    features/
      studio/               стан через SSE, перепідключення, довідка
      generation/           форма, оцінка, надсилання, результати й картка відео
      assets/               бібліотека, завантаження референсів, розмітка кадру
      billing/              баланс та історія кредитів
    lib/format.ts           форматування чисел і дат
    styles/                 стилі за розділами
    styles.css              порядок підключення стилів
  server/
    main.ts                 запуск API, callback і вбудованого worker
    worker-main.ts          окремий процес worker
    migrate.ts              команда міграцій
    config.ts               читання та перевірка змінних середовища
    errors.ts               помилки застосунку та провайдера
    http/                   маршрути, callback, SSE, знімок стану
    jobs/                   валідація, worker, черга, правила повторів
    billing/                оцінка, резерв, списання, повернення, грошова арифметика
    assets/                 завантаження, кеш і підготовка референсів
    media/                  перевірка файлів, завантаження й зберігання результату
    db/                     з’єднання, транзакції, міграції та типи рядків
    providers/              контракти, APIMart, mock і створення адаптерів
  shared/contracts.ts       типи публічного API
```

## Підключення іншого провайдера

Загальний контракт — `VideoProvider` у `providers/types.ts`: `submit → poll → result`. Він повертає нормалізовані статуси, собівартість і джерело файла. Worker не знає HTTP-формату APIMart; фінансові операції та локальне збереження не залежать від конкретного адаптера.

Щоб підключити інший API:

1. Додайте адаптер у `providers/`, реалізуйте три методи й перетворення помилок на `ProviderError`. `submit` отримує стабільний ID задачі як ключ ідемпотентності. Неоднозначну відповідь на запуск потрібно позначати `submissionUncertain`.
2. Додайте фабрику адаптера в реєстр `providers/create-providers.ts`. Фабрика отримує `config`, `env` і pool; налаштування конкретного API та їхня перевірка залишаються всередині адаптера. Невідомий або неналаштований вибраний провайдер зупиняє запуск.
3. Укажіть його ID у `PROVIDER_MODE` та потрібні змінні середовища. Для Docker передайте нові змінні через `environment` або Compose override. Змінювати worker, billing, HTTP-маршрути, загальні типи чи схему БД для нового ID не потрібно.

Назва в інтерфейсі надходить із `displayName`. ID провайдера — рядок, а не перелік APIMart/Mock; поле `jobs.mode` зберігає цей ID для відновлення старих задач навіть після зміни активного провайдера. Фабрики реєструють усі налаштовані адаптери. Для вже створених задач потрібно залишати їхні адаптери та облікові дані доступними.

Додаткові можливості підключаються через той самий контракт:

- `assets` реалізує `AssetProvider`: підготовка файла та перевірка статусу. Адаптер отримує локальний шлях, метадані, початкову URL і функцію `publish()` для тимчасового HTTPS-посилання. Він може повернути готову URL одразу або ID асинхронної підготовки. Сервіс зберігає статус і кеш, але не створює `ApiMartAssets` і не припускає схему `asset://`.
- `scope` відокремлює кеш конкретного провайдера й облікового запису. Нові адаптери мають задавати власний простір імен без відкритого ключа. Для APIMart збережено попередній SHA-256 ключа, щоб наявна бібліотека залишалася доступною; для mock — `mock`.
- `webhook` задає власний шлях і розбір payload/headers у task ID. HTTP-шар лише зберігає сигнал пробудження за парою `(provider ID, task ID)`. APIMart зберігає сумісний `/callback`; інші адаптери можуть мати інший маршрут і формат.
- `pollIntervalMs` задає резервний інтервал опитування, якщо адаптер увімкнув webhook. За відсутності цього значення діє звичайний backoff; глобальна URL сама по собі не переводить іншого провайдера в режим webhook.

Без `assets` генерація з тексту працює, а завантаження референсу повертає зрозумілу помилку без створення задачі чи резерву. Без `webhook` використовується polling. Контракт входу описує можливості однієї моделі цього сервісу: адаптер зіставляє їх зі своїм API або повертає контрольовану помилку для непідтримуваної операції. Динамічний каталог інших моделей не входить до цього розширення.

`tests/providers.test.ts` реєструє незалежний тестовий адаптер, який не успадковує APIMart або Mock. Через незмінні API та worker перевіряються референс, оцінка, резерв, сторонній формат callback, скачування, фактичне списання й повторні події. Окремо перевіряються polling без додаткових можливостей, ізоляція однакових task ID та міграція старої бази. Міграція v3 змінює лише обмеження на ID провайдера; баланс, задачі й файли не перераховуються.

## Worker і черга

`jobs/worker.ts` керує етапами submit → poll → збереження результату. SQL і створення адаптерів винесено з цього модуля. Точки запуску збирають провайдерів через `providers/create-providers.ts`; тести передають свої адаптери.

`jobs/job-repository.ts` відповідає за отримання задачі, продовження lease та переходи між станами. Публічні методи описують дії: `markSubmitting`, `recordProgress`, `retryDownload`. Спільний `transition` приватний. Зміни передаються в SQL іменованим JSON-записом через `jsonb_to_record`, а ID задачі та lease — окремими параметрами.

Захоплення використовує `FOR UPDATE SKIP LOCKED`. Lease діє 120 секунд і продовжується кожні 20 секунд. Перевірки фінансового стану, fencing token і строку lease входять до атомарного UPDATE. Застарілий worker не може змінити задачу після передавання іншому. Мережеві запити виконуються поза транзакціями.

Сповіщення надсилається в тій самій транзакції й стає видимим після COMMIT. Callback під час GET провайдера не губить сигнал пробудження; `Retry-After` залишається окремим обмеженням запуску. Колонка БД `poll_attempt` історично рахує всі переходи worker, включно з submit і завантаженням. У `WorkItem` вона має точнішу назву `processing_attempt`.

```text
queued → submitting → pending / processing → downloading → completed
                    ↘ submission_unknown → timed_out
будь-який незавершений стан → failed / timed_out
```

Перед POST зберігається `submitting`. Втрата відповіді, неоднозначний 5xx або перезапуск у цій точці без provider id призводять до `submission_unknown`. Автоматичного повторного платного запуску немає; резерв утримується до загального дедлайну. Стабільний `Idempotency-Key` додатково захищає дозволені повтори, зокрема після підтвердженого 429.

### Помилки та повтори

| Ситуація                                  | Поведінка                                                                    |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| 400 / 401 / 402 / 403                     | Завершення з повідомленням та повним поверненням резерву                     |
| 429                                       | Backoff і `Retry-After`; підтверджену відмову під час submit можна повторити |
| 5xx або втрата з’єднання під час GET      | Повтор до загального дедлайну зі збереженням резерву                         |
| 5xx або втрачена відповідь під час POST   | `submission_unknown`, без непідтвердженого повторного запуску                |
| Асинхронний `failed` / `cancelled`        | Повне повернення; собівартість провайдера зберігається, якщо отримана        |
| Помилка завантаження або пошкоджений файл | До трьох спроб отримання й перевірки файла, потім повернення                 |
| Тимчасовий збій result endpoint або БД    | Не витрачає ліміт спроб перевірки медіафайла                                 |
| Загальний таймаут                         | Повне повернення; пізнє завершення не спричиняє списання                     |

Backoff зростає експоненційно з верхньою межею 30 секунд і jitter до 1 секунди; він залежить від лічильника переходів. Mock опитується раз на секунду, APIMart із webhook — раз на 60 секунд як резервний механізм. Загальний дедлайн типово становить 20 хвилин від створення задачі, включно з чергою. Прострочені задачі звільняються під час наступного доступного проходу worker; без нього залишаються в PostgreSQL.

## Фінанси та база

`billing/credits.ts` зберігає пов’язані зміни гаманця, задачі та ledger в одній транзакції. Порядок блокувань — `users` → `jobs`. Розділяти фінансову операцію на незалежні repository-виклики з власними транзакціями не можна: це порушило б атомарність. SQL тут навмисно залишається поруч із фінансовими правилами.

`billing/quote.ts` визначає тариф, очікувану вартість і резерв: задана тривалість +1 с виходу; auto/Edit — до 30 с виходу. `money.ts` виконує точну арифметику. Суми — цілі milli-credits, тривалість — цілі мікросекунди. Знімок тарифу, ключ ідемпотентності та збережений резерв не перераховуються після перезапуску.

Операції `hold`, `settle` і `release` захищені транзакціями, унікальністю `(job_id, kind)` і CHECK-обмеженнями. Після `settled` або `released` повторні та пізні результати не змінюють баланс. Обмеження списання резервом і окремий облік перевищення описані в [README](../README.md#запас-до-резерву).

`db/connection.ts` містить pool, транзакції та NOTIFY; `db/migrations.ts` — схему й міграції; `db/rows.ts` — типи рядків БД. PostgreSQL bigint/numeric надходять як рядки, timestamptz — як Date. Версії схеми зберігаються в `schema_migrations`; повторний запуск міграцій не скидає баланс і задачі.

## Медіафайли та референси

Результат спочатку записується під тимчасовим ім’ям, перевіряється ffprobe й атомарно перейменовується. Ім’я містить ID задачі та lease token: застарілий worker не перезаписує файл іншого. `completed` з’являється лише після фінансового COMMIT. Медіамаршрут видає файл завершеної оплаченої задачі й підтримує byte ranges. Після неоднозначного COMMIT файл зберігається, щоб не видалити вже оплачений результат.

Завантаження результату дозволяє лише публічний HTTPS, до трьох перенаправлень, 200 MB і 60 секунд. DNS-адреса перевіряється та фіксується для з’єднання; Bearer-ключ не передається CDN. ffprobe запускається без shell, з файловим протоколом, MP4/MOV-демультиплексором і лімітом 15 секунд.

`assets/service.ts` відповідає за локальне завантаження, HTTPS-імпорт, SHA-256 кеш, стан підготовки через `AssetProvider` і повторне використання готової генерації. `media/inspect-asset.ts` перевіряє фактичний формат, розміри та тривалість. Браузер не визначає довірені секунди, вартість чи шлях файла. Правила режимів — у [modes.md](modes.md).

## HTTP, webhook і SSE

Основний listener на порту 3000 містить UI, фінансові маршрути, бібліотеку й локальний плеєр. Окремий listener на 3001 обслуговує callback і тимчасові посилання на конкретний референс.

Callback — сигнал перевірити відомий `provider_task_id`. Перед відповіддю 2xx він зберігається в БД; статус, URL та суми з тіла не завершують задачу. Worker отримує їх авторизованим GET. Невідомі, повторні й пізні події підтверджуються без повторних фінансових операцій; пробудження однієї задачі обмежене одним разом на п’ять секунд. Для відкритого промислового розгортання потрібна специфікована провайдером перевірка підпису.

SSE працює через PostgreSQL `LISTEN/NOTIFY`, тому окремий worker може оновлювати браузер через API. Heartbeat — кожні 15 секунд. Після події клієнт отримує свіжий знімок стану; повторне підключення, фокус вкладки й контрольна синхронізація відновлюють пропущені оновлення.

## Інтерфейс і перевірки

- `useStudioState` — завантаження стану та SSE.
- `useEstimate` — debounce й скасування застарілої оцінки.
- `useGenerationForm` — стан форми, відновлення непідтвердженого запиту з тим самим ключем і вибір відео для Edit.
- `useAssetLibrary` — завантаження та перевірка готовності референсів.

Компоненти відображають дані цих хуків. CSS розділено за розділами інтерфейсу; `styles.css` задає порядок каскаду, зокрема адаптивних правил.

`npm test` використовує тимчасову PostgreSQL та mock-сховище; спільний життєвий цикл — у `tests/helpers/test-context.ts`. Окремо перевіряються фінанси, worker, HTTP, repository, режими, адаптер і взаємодія процесів. `npm run build` очищає `dist`, перевіряє TypeScript і збирає клієнт/сервер. Увімкнено `noUnusedLocals` та `noUnusedParameters`; форматування перевіряє `npm run format:check`.
